| 2026-08-01 | **A green harness is not a passed gate** | The Day-2 gate says "no fault, collision, or manual correction". | 2026-08-06 | **A frame-index recorder would silently misalign the cameras** | Measured: the two cameras differ by 0.28 ms/frame in delivered rate (33.02 vs 33.30 ms mean interval), both within a whisker of the requested 30 fps. Index-paired offset therefore accumulates without bound — 76 ms over 150 frames — so frame i of one stream and frame i of the other are more than a whole frame apart within about 120 frames. Free-running USB cameras with no hardware sync always drift; nothing is wrong with the hardware | The recording path MUST pair frames by timestamp, never by frame index. `b601.cameras.sync` reports the drift rate and index offset as diagnostics for exactly this reason, and its verdict uses nearest-timestamp pairing (9.04 ms p95 on the same recording, 0.27 of a frame period). **Verify the pairing model in the recording code before the first pilot episode** | **open — blocks recording** |
| 2026-08-06 | **A camera setting can be written, reported successful, and not take** | Measured: the UVC camera silently IGNORES a write to `exposure_time_absolute` while in Aperture Priority mode — the control reads `flags=inactive` until `auto_exposure=1` (Manual Mode), and V4L2 reports the write as successful either way. The two backends also disagree on what 'off' is: 1 on this V4L2 device, which offers no 0 at all, and 0 on RealSense. A capture path that assumed a boolean would leave a camera on auto while reporting success | `b601/cameras/capture.py` disables the automatic control BEFORE writing the value it gates, and READS BACK every write, treating a value that did not move as an error rather than a log line. Verified end to end on both cameras 2026-08-06: reset to auto, applied, and confirmed from an independent process. Run `python -m b601.cameras.capture` before every session — a `hardware_reset()` or replug restores defaults | mitigated |
| 2026-08-06 | **A stalled camera reports perfectly healthy settings** | ROOT CAUSE FOUND 2026-08-07, after THREE wrong attributions (pipeline open/close cycles, a wedged hub, then the USB 2.1 link — the last one written here as "found"). Reproduced on a fresh USB 3.2 link and bisected: it was TWO stacked defects. **(1) Vendor null-frame bug:** `get_depth_frame()` on a colour-only frameset returns a null frame that is falsy but *not None*; the snapshot builder tested `is not None`, called `get_data()` on the null handle, and threw `null pointer passed for argument "frame_ref"` for EVERY frameset — which the read loop classifies as a transient startup error and suppresses at debug forever. The manager reported `frames_seq: 0` while a main thread polling the SAME pipeline object received 60/60. **(2) One-session-per-reset firmware behaviour** (own row below), which is what made raw checks pass and the recording that followed fail, and made every reproduction attempt contradict the last | Defect 1 fixed in the vendor tree (commit `3b4f877`, `LEROBOT_ORIGIN` re-pinned): the checks now use truthiness, the librealsense-documented null test. Verified: `async_read` 90/90 at 30.4 fps. Defect 2 is handled by `b601.cameras.reset` in the session script. The USB link check in preflight STAYS, re-justified as a bandwidth gate (its docstring now records the corrected story — a check whose failure story is wrong teaches the wrong remedy) | mitigated — fix committed and verified |
| 2026-08-07 | **The D405 streams exactly ONE pipeline session per hardware reset** | Measured on fw 5.12.14.100, USB 3.2, raw pyrealsense2 with no LeRobot code: after a reset, session 1 delivers 30/30; sessions 2, 3, 4 (immediately, +5 s, +15 s) each open successfully, negotiate the correct profile, and deliver **0/30**. Only `hardware_reset()` restores it. Consequence: ANY diagnostic that opens a pipeline — preflight liveness, a quick manual check — silently kills the recording that follows, which is exactly how attempt 4 died on a camera preflight had just passed. Also measured: options set WITHOUT a pipeline do not consume the session and persist into the next one, so settings application is safe | `record_session.sh` gate 4: after preflight, `b601.cameras.reset` hardware-resets the D405, waits for re-enumeration plus a settle delay (enumerated ≠ ready, measured), then re-runs capture because the reset wipes sensor options. Candidate REAL fix: firmware update — 5.12.14.100 is early D405 firmware and this smells like a known-fixed defect. That is an owner decision (small brick risk, changes pinned hardware state) and is NOT scheduled | **open — worked around; firmware update is the candidate close** |
| 2026-08-06 | **The wrist exposure placeholder would blur every grasp frame** | The D405's auto-selected exposure was 33000 us. At 30 fps the frame period is 33333 us, so that exposes for essentially the whole frame — on a MOVING wrist camera, maximum motion blur in the one sensor Day-16 grasp verification depends on. `cameras.json` carries 8000 us instead, which is roughly a quarter period and is **chosen, not measured**. AND THE RISK LANDED, in the other direction: episode 0 (2026-08-08) recorded a near-black wrist stream — mean brightness 5–16/255, sharpness ~3–31 — because 8000 us at the gain floor (16) is far too little light for this room. The blur guard worked; nothing was measured behind it | MEASURED 2026-08-08: a 10-point exposure×gain sweep in one live session with the arm posed mid-grasp. Chosen: 8000 us + gain 248 (device max) — mean 85, block and fingers clearly resolvable. Exposure stays at a quarter period deliberately: the wrist camera moves, and blur corrupts the approach frames where the policy acts most, while gain noise averages out. Manifest updated, applied, read back. Episode 0's wrist stream is quarantined as untrainable in `dataset_card.md`; the replay it validated (Day-5 currency) uses no images | mitigated — measured, applied, episode 0 caveated |
| 2026-08-06 | **A constant camera latency offset is unmeasurable from timestamps** | `b601.cameras.sync` reads host arrival times, the only clock a RealSense pipeline and a V4L2 capture share. A passing sync check is therefore not evidence against a constant skew | Stated in the module docstring and asserted as a blind spot in the test suite so it is not mistaken for coverage. Measuring it needs a physical event visible to both cameras — fold into the Day-3 calibration procedure rather than trusting the sync check | monitoring |
